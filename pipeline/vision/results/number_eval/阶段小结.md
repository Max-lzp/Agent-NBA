# 号码识别基线评测 — 阶段小结（2026-10-10，进行中）

评测对象：`data/2025-26/frames` 官方录像帧数据集（249 剪辑/5252 帧，标签=投篮人官方背号）。
方法：生产同款 player_detector(conf=0.5) → 躯干裁切 → RapidOCR，每帧取最大 6 个球员框。
口径：帧级「投篮人号码是否出现在该帧 OCR 结果中」。评测脚本 `eval_number_dataset.py`。

## 中间数字（16 剪辑 / 326 帧，全部来自 0022500160，后台仍在跑全量）

| 指标 | 值 |
|---|---|
| 帧级命中率 | **7.9%**（24/305） |
| 剪辑级命中率（任一阵命中） | **56%**（9/16） |
| miss_with_reads（有读数但没中） | 54.8% |
| no_read（有球员框但无有效数字） | 29.2% |
| no_player（无框） | 8.2% |

## 两个重要发现

1. **最佳读数窗口在投篮前段，不在出手瞬间**。命中帧 64% 落在剪辑前 2/3
   （进攻站位阶段，投篮人常面向镜头）；最后 1/3（起跳出手+落地，基本背对镜头）
   命中率仅 1/102。给下游的建议：号码投票多取投篮前的站位帧，别盯着出手帧。
2. **OCR 读数本身质量不差**——miss 帧读到的多为场上其他人的真实号码
   （如真值 32 时读到 7/3/15），典型问题是「读得到号码但不知道哪个是投篮人」，
   这正是排除法/轨迹合并要解决的；纯读不出（no_read）占 29%，多是远景+侧身。

## 运行方式（复跑/续跑）
```bash
cd pipeline/vision
.venv/bin/python eval_number_dataset.py --workers 5          # 全量（断点续跑）
.venv/bin/python eval_number_dataset.py --aggregate-only     # 只汇总
```
注意：本机为 10 核桌面环境，多进程下 RapidOCR/torch 线程必须限制
（脚本已限 2 线程/worker），且桌面负载高时单剪辑可慢至 2-3 分钟。

## 追加（10-10 11:10）：采样策略 A/B（72 剪辑，推翻早前猜测）

| 策略 | top-4 | top-6 | top-8 |
|---|---|---|---|
| 现状：全剪辑按框大取 | 38% | 47% | **54%** |
| 仅前 2/3 剪辑 | 40% | 46% | 49% |
| 仅前 1/2 剪辑 | 40% | 44% | 46% |

「站位帧优先」只在极小预算（top-4）略有优势（+2 剪辑），在生产实际用的 top-8 反而更差。
命中帧位置中位数 0.41——略偏前但散布广。**结论：不要砍窗口，框大 top-8 已接近采样上限；
提升空间在读数质量（专用模型）与归属（官方事件对人），不在采样。**

## 追加：官方事件邻接表（任务②的素材）

每个投篮剪辑挂上时间窗内的官方非投篮事件（篮板/抢断/失误/犯规/盖帽，带 actor 官方背号

注意：playbyplay 的 clock 是 ISO `PT00M46.30S` 格式，不是 M:SS。

## 追加（10-10 11:20）：「OCR 投票+官方事件」端到端 demo（77 已评测剪辑）

- 投篮人命名：纯 OCR 投票 52%（40/77），加官方事件旁证后 **52%（+0）**。
  零救回——方向搞错了：投篮人本来就从投篮日志已知，事件旁证投错地方了。
- 重新按正确口径量化全表（693 投篮）：
  **投篮后具名事件 22%**（153 个投篮有具名篮板/盖帽/造犯规人 → 可直接给
  「拿到球的轨迹」对人）；投篮前具名事件 54%（失误/抢断/犯规链）；纯 TEAM 事件仅 2%。
- 结论：事件对人要接在**球权/轨迹层**（apply_jersey_ocr 的 ball_handler 之后、
  或 refresh_identity 的轨迹合并里），不要接在投篮人确认上。
