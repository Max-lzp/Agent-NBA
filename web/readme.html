Deep Court

Deep Court 读取一段 NBA 比赛视频和官方深度数据，在云上生成带记分牌、人名和数据的回放；分析师跑在 Amazon Bedrock AgentCore 上，观众从 Amazon CloudFront 打开成片。

让每一次出手被重新讲述一遍。打开这个域名就是成片回放，不用选文件，也不用等分析跑完。

作品亮点

  1. 比分条跟着记分牌走：节次、比赛钟、客队和主队比分。出手后约三秒弹出这一球的预期命中率、区域和距离。
  2. 这一回合场上 10 个人先对上身体：号码、持球和领防是钉子，剩下的人只在同队还空着的坑里排除。成片前 3 秒标出已经对上的人，之后只标持球人、传球双方和领防人。两个差不多高、又没有号码的坑先空着。这是训练片在本机上的做法。考试片改由云上认人，规则在第 5 步。
  3. 暂停后展开官方逐回合原文、助攻和当时场上的十个人。半场图上的点用官方坐标。
  4. 播放器可以选英文原声或中文解说。中文是整段英文解说的译文，用 Amazon Polly 的知语说出来，不再只写两句，原解说也不留在这条音轨里。

AI Agent 做了什么

Amazon Bedrock AgentCore 运行时的名字是 DeepCourtAnalyst，也就是 Deep Court 分析师。它不看图编事件。事件已经写在结构化清单里。分析师的工作是查数据，再写观众听得懂的解说。

运行时用 Amazon Bedrock 的 Converse 接口调用 global.anthropic.claude-sonnet-4-6（Claude Sonnet 4.6）。第一轮必须先调用工具，后面由模型自己决定还要不要再查。它可以使用的工具有五个：

  • read_manifest：读本段回放的事件清单 structured/{jobId}.json，里面是回合、接球、传球，以及清单里已经对上的官方出手。
  • validate_manifest：校验清单格式。版本必须是 0.1，回合不能空，进攻方只能是火箭或独行侠。
  • read_official：读媒体桶 official/2025-26/ 的官方逐回合和 shot quality。预期命中率已经换成 0 到 100 的百分数。清单里没有这段的比赛钟时，不返回整场出手，避免把别的回合说成这一段。
  • read_season：读 2025-26 赛季火箭、独行侠的攻防三区（近框、其余两分、三分）和个人资料。数据打进运行时的 season_hou_dal.json。空值保持空，不当成 0。出手数为 0 时不给命中率。
  • read_identity：读认人结果 identity/{jobId}.json。解说里的姓名、球队和号码只能来自这份结果。

每句中文和英文都要过一遍落地校验：句子里的数字必须出现在工具结果里，人名必须出现在工具结果里，命中率旁边的数字必须来自百分数字段。对不上的句子删掉，不改写成一个新数字。查不到就不写。问分析师时如果工具里没有足够的数据，回答固定是「工具里没有足够的数据来回答这个问题。」管道模式要写满三条亮点；凑不满时，空位写明这段没有更多能对上官方或赛季数据的看点。

通过校验的解说写到媒体桶 analysis/{jobId}.json。网页上的「问分析师」把问题发到 /api/agent/ask。Amazon CloudFront 去掉 /api 前缀后，Amazon API Gateway 的 POST /agent/ask 交给 Lambda ask_agent，叫醒的仍是同一个运行时。已经写好的解说用 GET /agent/analysis/{jobId} 读取。客户端在 web/analyst.js。

部署之后，状态机在 AWS Batch 成功时调用 Lambda analyze_job，再由它叫醒分析师。structured/ 不再发 Amazon S3 通知。上下文 enableOrchestration=false 时，仍由这条通知叫醒。运行时冷启动或调用失败时，analyze_job 直接读清单，把页面事件写入 Amazon DynamoDB，回放不会停在分析中。清单格式不合法时任务写成失败，不把坏清单放进页面。模型没有返回可用解说时，运行时仍把清单交还给 Lambda，页面事件照常写入。

下午探测时，运行时 30 秒内没有完成初始化：入口导入了没有打进代码包的库，进程一起床就退出。现在入口先用 Python 标准库响应 /ping，boto3 由 CDK 打进代码包，第一次分析才加载。这段分析师代码还没有用当前模板执行 cdk deploy，所以这一节的状态是部署中。页面事件写入本身已经在用。

Bedrock 做了什么

Amazon Bedrock 在这条管道里承担两类模型调用，都走 Converse，区域是 us-east-1。视觉认人和文字解说分开，解说模型不看画面编事件。

认人：Qwen3 VL

已接通

考试片在 inference/chain.py 里调用 qwen.qwen3-vl-235b-a22b。每条轨迹挑选框够大、重叠少的帧，最多 12 帧。模型读球衣号码和球衣颜色，并判断这个人是不是裁判。温度是 0，回复要求是一份 JSON。

多帧投票定号码，至少两票，并且要多于第二名，否则号码作废。Amazon Rekognition 的 DetectText 把读到的号码投进同一轮，算第二票。Qwen 调用失败时才用 Amazon Textract 的 DetectDocumentText 兜底读号码。裁判那段轨迹切出去，不投票，也不挂标签。

场上 10 人由这场官方逐回合里的换人推出来。号码只和球衣颜色那一队、这一刻的场上 5 人匹配。颜色和号码对不上就不写名字。同一个名字只留在票数最多的那条轨迹上，名签从这条轨迹的第一帧挂到结尾。名签贴在头顶上方，最多上挪一行；「Agent detecting」放不下就不画。分得出队但没有名字的人，标签只写 Agent detecting，颜色用队色。分不出队的不挂标签。官方逐回合里的得分人和助攻人先钉上。

探测片 qwen-flagg 第 1 秒写出小史密斯、弗拉格，两人都在场上，裁判身上没有标签。其余分得出队的 4 人挂 Agent detecting。整段 10 个名字各留一条轨迹，球衣颜色都和队一致。认人多花 114 秒。训练片的身体坑和排除法仍在本机 pipeline/vision/backtrack.py。

解说：Claude Sonnet 4.6

部署中

分析师推理用的是上面的 global.anthropic.claude-sonnet-4-6。跨区域推理配置和底层模型的调用权限都写在 AgentCore 运行时角色上，动作包括 bedrock:Converse。温度是 0。它只根据工具返回的内容写回合解说、定格卡和三条亮点。

栈里另有一条 POST /commentary。它用同一个模型写两句短解说，再用 Amazon Polly 合成，失败不影响分析任务。播放器上的中文音轨不走这条接口。

认人和语音旁边的托管服务

已接通

Amazon Rekognition DetectText 是号码的第二票，和 Qwen 的读数放进同一次多数票。Amazon Textract DetectDocumentText 只在 Qwen 调用失败时读号码。记分牌上的 Textract 只做过探测，不在主路径；CDK 里的 OcrScoreboard 函数主路径不调用。记分牌主路径是同一台机器上的 RapidOCR，检测边长限制 640。

中文音轨在成片之后、同一容器里做。Amazon Transcribe 转写英文原声。常见的人名听错先改掉，再交给 Amazon Translate 译成中文。Amazon Polly 用 Neural 引擎、语音知语（Zhiyu）、语言 cmn-CN，按原句时间合成。普通话在 Polly 里这条神经语音是知语。现场声和原解说叠在一起，声道又几乎是单声道，分不开，所以中文音轨只有合成人声，原解说不留在里面。英文音轨就是成片里的原声。

仓库里有篮球术语表 data/terminology/basketball-en-zh.csv，导入脚本交给 Amazon Translate 时的名称是 deepcourt-basketball。音轨代码只有在环境变量 TRANSLATE_TERMINOLOGY 写了这个名字时才带上术语表。当前 Batch 作业定义没有这个变量，探测片的翻译请求不带术语表。术语表不存在或没有权限时，同一句去掉术语表再译一次，音轨不会因此中断。

探测片 warm-probe 的中文音轨已经在播放器里。训练片弗拉格、阿门的两条音轨是本机做的，已经放在网页桶。

逐步说明

每张卡片对应全景里的一步：业务流程、对观众和解说的意义、用到的亚马逊云服务、现在的状态。

1. 收片

主路径

业务流程。训练片或考试片进入管道。上传页经 Amazon CloudFront 的 /api/* 调用 Amazon API Gateway POST /jobs。Lambda create_job 在 Amazon DynamoDB 的 JobsTable 记下任务，返回 Amazon S3 预签名地址。浏览器把视频直传到媒体桶 raw/{jobId}/。create_job 不提交计算，也不启动状态机。run_clip 也可以直接读本地文件。

业务意义。评委打开的是成片，不是上传页。上传页在 /index.html，只给我们自己把片子送进管道。视频不经过应用服务器。

  • Amazon S3 raw/
  • Amazon API Gateway
  • AWS Lambda create_job
  • Amazon DynamoDB JobsTable
  • Amazon CloudFront

栈 Team04DeepCourt 已创建。分配 d2vzd2batw1eqe.cloudfront.net 已部署。部署之后，raw/ 的对象创建才由 Amazon EventBridge 启动状态机。

2. 编排

部署中

业务流程。状态机 deepcourt-film 是标准工作流，代码在 cdk/lib/orchestration.ts。由 AWS CDK 定义。部署之后，上传即自动跑完全流程：Amazon EventBridge 规则 deepcourt-raw-upload 只匹配媒体桶 raw/ 的对象创建；状态机把任务写成 TRACKING，向 AWS Batch 提交作业并等到结束，再调用 analyze_job，然后核对网页桶里的成片和 replay/clips.js，失效 /assets/{jobId}-broadcast.mp4、-zh.mp4、-en.mp4 和 /replay/clips.js。失败写成 FAILED，并记下是哪一步。同一次上传的重复事件由 DynamoDB 条件挡住，停在 DuplicateSkipped。-c enableOrchestration=false 时不接 EventBridge，S3 仍通知 analyze_job。

业务意义。上传之后只有一条路。不会在文件还没传完时启动，也不会和手工提交各跑一遍。观众等到的是同一支片子的成片、片单和事件。

  • AWS Step Functions
  • Amazon EventBridge
  • Amazon DynamoDB
  • AWS Batch
  • AWS Lambda analyze_job
  • Amazon S3
  • Amazon CloudFront

代码已合入。这次栈更新还没部署，考试片仍走已经部署的作业定义。状态机用服务直连，不另包一层专门提交作业的 Lambda。SubmitTrack 留着，没有事件源。

3. 追踪

已接通

业务流程。YOLO 检测人和球，ByteTrack 串成轨迹。一次看 16 帧，不跑球场关键点。部署之后由状态机对队列 deepcourt-track 做同步提交。部署前仍是手工提交作业。机器是 Amazon EC2 c7i.48xlarge，磁盘是 Amazon EBS gp3 1000GB，镜像在 Amazon ECR deepcourt-tracker:ready。轨迹写到 S3 tracking/，启动脚本从 S3 bootstrap/track/ 拉下来。本机 MPS 仍能出训练片。

业务意义。后面的认人、持球和传球都站在这条轨迹上。没有轨迹，画面上就没有人和球可标。

  • AWS Batch
  • Amazon EC2 c7i.48xlarge
  • Amazon EBS gp3
  • Amazon ECR
  • Amazon S3
  • Amazon VPC

G 和 VT 实例配额为 0。标准配额 256 vCPU，这台机器用其中 192，并且保持开着。镜像已烤好。探测作业 warm-probe 写出 39 帧轨迹。计算环境在本栈的 VPC 里，公有子网，没有 NAT。实例角色包含 SSM，用来管理这台主机。

4. 记分牌

已接通

业务流程。考试片在同一台 c7i.48xlarge 上跑 pipeline/vision/scoreboard.py。RapidOCR 读节次、比赛钟、进攻钟和比分，检测边长限制 640，避免整幅画面把读数拖慢。训练片仍在本机。Amazon Textract 的 DetectDocumentText 只做过探测，不在记分牌主路径。

业务意义。记分牌是转播自己打上的时钟和比分。节次、比赛钟和比分用来对上是哪一场、哪一个回合，也用来把比分条烧进成片。观众看到的时间以记分牌为准。

  • Amazon EC2 上的 RapidOCR
  • Amazon Textract 仅探测

warm-probe 读出 6 条比分条。训练片主路径仍在本地。

5. 认人

已接通

业务流程。考试片把轨迹帧交给 Amazon Bedrock 上的 Qwen3 VL，读号码和队色，多数票定号码。Amazon Rekognition 算第二票。裁判排除。号码只在同队、这一刻的场上 5 人里对。分得出队但没有名字就挂队色标签 Agent detecting。得分人和助攻人先按官方逐回合钉住。结果写到 S3 identity/。Qwen 失败时 Amazon Textract 兜底。训练片算法仍在本机。

业务意义。解说和名签要有人名。认不出就标明正在识别，不把猜出来的名字贴到人身上。观众能分清谁已经对上，谁还只有队色。

  • Amazon Bedrock Qwen3 VL
  • Amazon Rekognition DetectText
  • Amazon Textract 兜底
  • Amazon S3 official/ 与 identity/

细节和探测结果见上面「Bedrock 做了什么」。

6. 事件清单

已接通

业务流程。考试片按球在谁脚下写出接球和传球。比分跳动再对上官方出手。清单写成媒体桶 structured/{jobId}.json。部署之后由状态机调用 analyze_job，structured/ 不再发 S3 通知。分析师读这份清单，把回合解说写到 analysis/{jobId}.json。训练片仍在本机找脱手帧和领防人，代码在 pipeline/events 和 pipeline/vision/release.py。

业务意义。时间线上的事件来自这份清单，不来自模型看图。解说如果要提到一次传球或一次出手，得先在清单里有这一笔。

  • Amazon S3 structured/
  • Amazon S3 analysis/
  • AWS Lambda analyze_job
  • Amazon Bedrock AgentCore
  • Amazon DynamoDB

warm-probe 的清单是 3 条事件，Jobs 表状态 DONE。分析师解说的状态见第 9 步。领防和脱手帧仍在本地。

7. 官方数据

已接通

业务意义。预期命中率、助攻和落点来自官方深度数据。暂停后展开的原文和半场图因此和转播记录对得上，不是画面估算。

  • Amazon S3 official/

探测片对上比赛 0022500356。这 5 秒里比分没有跳动，所以没有出手行。训练片的其余官方字段仍在本地。

主路径

业务流程。考试片把 structured/{jobId}.json 写进媒体桶 team04deepcourt-mediabucketbcbb02ba-haisfxujonfg。这一步是第 6 步的落点：文件进桶之后，校验和分析师才有输入。

9. 校验

主路径

业务流程。Lambda analyze_job 取回清单，校验格式，写成页面事件，放进 DynamoDB EventsTable。分析师另外把解说写到 S3 analysis/。AgentCore 冷启动或调用失败时，Lambda 直接读清单写事件。部署之后只由状态机调用。日志在 Amazon CloudWatch Logs，保留 7 天。

业务意义。回放时间线不依赖分析师是否醒着。分析师醒着时，解说和亮点用的是同一份已经校验过的清单。

  • AWS Lambda analyze_job
  • Amazon Bedrock AgentCore DeepCourtAnalyst
  • Amazon DynamoDB EventsTable
  • Amazon CloudWatch Logs
  • Amazon S3 analysis/

事件写入已在用，所以这一步标主路径。分析师这次的工具调用运行时是部署中，见「AI Agent 做了什么」。

10. 回放

主路径

业务流程。浏览器打开成片、时间线，暂停可以展开。进球后跳回出手帧，定格 5 秒：投篮人脚下画红圈，弹出投篮人和领防人的队内排名星级，定格卡不再烧比分条。领防人脚下画黄色虚线圈，领防名签贴在他躯干旁、背向投篮人一侧。领防人号码没读出就只写没读出。右栏是分区热区图，红圈标出这一投。带任务号时，页面轮询 Amazon API Gateway GET /jobs/{id} 和 GET /jobs/{id}/events，由 Lambda get_job、list_events 读取。考试片的 mp4 和 replay/clips.js 用新文件名直传网页桶，只失效这几个路径。

业务意义。观众可以停在这一球上，看见谁投的、谁在防、这个位置的预期命中率，而不只是把进球再看一遍。

  • Amazon API Gateway
  • AWS Lambda get_job
  • AWS Lambda list_events

服务总表

下表只列仓库里真实出现、并且已经接通或已由 CDK 定义的服务。托管版指用亚马逊云服务的托管能力，而不是在比赛机器上自建一套等价系统。

服务用在哪一步为什么用托管版
Amazon CloudFront 1 收片，2 编排，13 网页 赛题要求用 CloudFront 发布。网页桶不公开，只允许源访问控制读取。/readme 和 /api 用函数改写路径。
Amazon S3 1、6、7、8、11、12、13 原始视频、清单、官方数据、认人结果、解说和成片都是对象。浏览器拿预签名地址直传，不经过应用服务器。
Amazon API Gateway 1 收片，10 回放，问分析师 REST API：POST /jobs、GET /jobs/{id}、GET /jobs/{id}/events、POST /agent/ask、GET /agent/analysis/{jobId}。浏览器不直连执行地址，走 CloudFront 的 /api/*。
AWS Lambda 1、2、6、9、10，以及问分析师 建任务、校验、读状态、读事件、叫醒分析师都是短请求。没有常驻的接口进程。日志进 CloudWatch，保留 7 天。
Amazon DynamoDB 1 任务，2 去重，9 页面事件 JobsTable 和 EventsTable 按 jobId 查询，按需容量。任务状态和事件列表分开。
Amazon EventBridge 2 编排 只有 raw/ 对象创建才启动状态机。建任务的接口不提交计算。状态：部署中。
AWS Step Functions 2 编排 标准工作流把收片、Batch 等待、校验和缓存失效串成一条，用服务直连。失败写回任务表。由 CDK 定义，上传即自动跑完全流程。状态：部署中。
AWS Batch 3 追踪，以及同一作业里的 4、5、11、12 追踪要一台固定的大机器。托管计算环境把 c7i.48xlarge 保持在 192 vCPU，队列负责投递。作业容器信任 ecs-tasks.amazonaws.com。

基础设施即代码

栈名 Team04DeepCourt，代码在 cdk/。账号 382918437747，profile nba，区域只有 us-east-1。标签是 team=04、stage=prod、project=deepcourt。部署身份代入 NBAHackathonParticipantRole。参赛角色不能脱离权限边界新建 IAM 角色。cdk/bin/app.ts 给这个账号上 CDK 创建的角色加上权限边界 NBAHackathonParticipantBoundary。

可信度

事件来自结构化清单。模型不看图编事件。页面中文音轨是英文解说的译文，不是模型看图写的。

记分牌读出节次、比赛钟和比分。追踪给出人和框。官方逐回合补上投篮人、助攻和预期命中率（xFG）。AgentCore 取回并校验这份清单；叫不醒时由 analyze_job 直接读同一份文件。

认人只在官方逐回合推出的场上 10 人里匹配，而且号码必须落在球衣颜色那一队这一刻的 5 人中。对不上名字、但分得出队，标签写 Agent detecting，颜色用队色。分不出队就不挂。裁判不挂标签。解说里的每一句中文和英文都要对上工具返回的数字和人名，查不到就不写。

决策反差是二次加工，不是另一套数据：预期命中率低于四成却进了，标成英雄球；高于六成却没进，标成可惜。其余出手只显示预期命中率本身。

引力和关键度来自官方赛季汇总。暂停后写在该球员这一球旁边，标明不是这一球的胜率变化。训练片的分差效率、引力和队内排名仍在本机计算。

和仓库里的 docs/pipeline-map.md 是同一张图。训练片是组委会发放的火箭、独行侠录像。考试片发布后再按同一条命令重跑，并在这里补上出处。
