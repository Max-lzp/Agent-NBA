# 关键决策记录

> 主人：C（呈现线）｜格式：每条 = 日期 / 背景 / 决定 / 理由 / 影响
> 这是决赛路演的弹药库——评委明说「把为什么这么做讲清楚比堆功能更打动人」。

## D-001 最小闭环优先

- 日期：2026-10-06
- 背景：三个硬性要求（AgentCore / CloudFront / CDK）+ 12 小时赛制
- 决定：用官方 CDK 模板先打通最小闭环（约半小时），再谈创意
- 理由：官方指南原话「剩下的时间用来做那个只有你们能想出来的东西」；20:00 硬截止，部署不能留到晚上
- 影响：模拟期头半天必须完成闭环演练

## D-002 抽帧策略：2–4fps 起步

- 日期：2026-10-06
- 背景：训练视频 1080p59.94，全帧处理配额与延迟都扛不住
- 决定：抽帧从 2–4fps 起步，按识别稳定性上调；关键事件段（出手前后）局部加密
- 理由：22 秒回合里真正信息量大的瞬间有限；配额要留给 18:00 后的考试视频调优
- 影响：影响 Qwen3 VL 调用成本与事件检测精度，模拟期压测定稿

## D-003 克制呈现原则

- 日期：2026-10-06
- 背景：NBA 产品经理明确警告「不要把数据简单堆叠在视频上」
- 决定：默认画面只放轻量标注（球员名 + 1 个关键指标），深度解读藏进点击/暂停
- 理由：克制 = UX 25 分的审美分；也是与堆数据队伍的差异化
- 影响：前端交互形态定为「时间线驱动 + 分层展开」

## D-004 视觉管线采用开源组件、全部本地推理

- 日期：2026-10-07
- 背景：任务①若全靠 Qwen3 VL 逐帧识别，额度与稳定性都是风险；GPU 配额为 0
- 决定：检测+跟踪用开源方案（abdullahtarek/basketball_analysis 主干 + roboflow/sports 零件），**全部本地 CPU 推理，不调任何外部 API**；Qwen3 VL 只保留三件事：读记分牌时钟、判战术事件、兜底难帧
- 理由：开源检测跟踪在体育视频上已高度成熟，预训练权重直接可用；本地推理零 token、零外网依赖，满足 key 保护纪律；比赛日识别跑本地，只把结构化 JSON 传 S3
- 影响：Bedrock 调用量降一个数量级，18:00 后考试视频调优余量充足；球衣号码 OCR 用 Roboflow 篮球专用数据集本地跑 + 号码→花名册映射

## D-005 交付形态：视频打底、交互拿分

- 日期：2026-10-07
- 背景：硬性要求第 2 条要求 CloudFront + Web 交互界面，录屏视频不算满足；UX 25 分明写评「操作性」
- 决定：ffmpeg 预渲染成片保底（打开即看）+ Web 播放器 Canvas 叠加层做三层交互（常驻轻量 → 暂停/点击展开 → 时间线双向绑定）；演示视频照录作为提交要件和保底路径
- 理由：成片保下限，交互撑 UX 25 分和决赛视觉 40 分上限；默认画面自解释，展开层「越看越有」
- 影响：Web 前端工作量上段位，C 线（呈现线）需按「作品级 Web 应用」标准排期
