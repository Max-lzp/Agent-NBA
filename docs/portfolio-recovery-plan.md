# Deep Court：投递版质量问题与推进方案

日期：2026-10-26。目标：在时间紧张的情况下，先形成一个精致、可信、能让招聘方看懂个人能力的项目演示，再开展竞品学习与能力扩展。

第一轮首屏与主回合精修已实施，布局对比和验证见 [polish-pass-1.md](polish-pass-1.md)。以下问题清单保留审查基线，不表示所有问题仍未处理。

## 当前判断

当前已经完成运行恢复，没有完成原作品展示质量恢复。原主题、比赛成片和数据快照已经可用，但主体验仍接近“历史回放 + 功能入口”，尚未充分呈现“帮助观众理解比赛”的产品价值。

前期偏差在于先处理可运行、网络、素材和发布，没有先确定原作效果的参照物、主展示回合和视觉验收标准。后续不再以“能打开、测试通过”替代作品质量验收。

当前基础是可复用资产，不需要推翻重写：原黑橙视觉、弗拉格成片、事件数据、球员信息、热区图、两个已核对的官方规则示例、静态部署和回归检查均保留。

## 问题清单与处理方式

| 优先级 | 具体问题 | 对投递的影响 | 解决方式 | 验收条件 |
| --- | --- | --- | --- | --- |
| P0 | 首屏先出现选择弹层、大段定位与术语，视频靠下 | 尚未体验价值就要求用户理解选项 | 默认新球迷模式，取消强制选择；首屏只留一句价值主张、主要演示及主操作；术语按需展开 | 390×844 和 1440×900 首屏均出现可操作播放器；首次点击即可播放 |
| P0 | 已烧录卡片细小，视频本身不能随观看模式减负 | 手机看不清；三种模式的承诺与实际效果不一致 | 优先找到匹配的干净视频，在网页层呈现关键解释；保留原成片为“比赛原版”。若原始素材不足，先用已核对短片做清晰示例，不冒称原全流程恢复 | 每个主展示回合均能看清人物动作和主要解释；核心文字位于响应式网页层；无重复卡片 |
| P0 | 模式差别主要是术语和球员列表，同一视频信息量不变 | 体现了用户分层概念，却没有证明体验差异 | 围绕同一事件定义三种内容：新球迷回答发生什么，普通球迷解释选择与空间，进阶观众展开指标和来源；不强行生成无依据战术结论 | 同一时刻三种解释有明确、可描述的差异；新球迷默认最多三个核心信息点 |
| P0 | 主播放器、官方规则页、个人案例、本地标记、技术归档分散 | 像多个工具拼接，缺少完整产品体验 | 保留单一主体验；规则示例纳入案例选择；技术归档与本地工具降为次级入口 | 主路径不离开体验即可完成“看一球—读解释—查出处”；主操作不超过三个 |
| P0 | 主页的“AI”定位与当前三条固定答案之间有落差 | 面试官可能把静态演示误认为实时 Agent，或看不出 AI 产品能力 | 静态部分明确称“引导式解释”；整理一个真实、可复核的 AI 案例，展示问题、工具查询、来源、答案与失败处理；无真实调用证据时不伪造 | 有能力状态表；实时能力以真实调用和日志验收，录制演示明确标注；固定答案不称大模型实时问答 |
| P0 | 缺少一条经过编排的演示叙事 | 有技术元素，但看不出普通球迷获得了什么 | 精修一个主回合：发生什么→为什么值得看→数据怎样帮助理解；用官方规则示例补充新球迷场景 | 60–90 秒演示能讲清用户问题、交互、来源与个人决策；即使网络不稳也能使用已验证的演示备份 |
| P1 | 事件快照含未完全确认的人名、传球和置信度 | 原版恢复不等于识别结果已正确 | 对主回合逐事件复核；区分官方记录、视觉推断和人工说明；删除或弱化无法确认的标签 | 主展示事件均有来源和复核状态；不把所有“传球”都作为官方事实 |

| P1 | 技术架构混合比赛时期与当前实现 | 无法判断哪些能力实际工作，个人工作也不突出 | 分成当前可体验、比赛历史实现、下一阶段三栏；个人案例用问题、决策、行动、证据写成短故事 | 面试官能在一分钟内找到个人职责、关键取舍及真实验证；不堆 AWS 服务列表 |

## 推进顺序与交付物

### 第一工作段：锁定参照物与演示范围

执行：以当前线上版本为可回退基线，确定一段主回合、首屏布局及三种模式的内容。列出原作与当前版本的对照矩阵，标明已还原、素材存在未接入、原始素材缺失、依赖实时服务四类。

交付：一页体验结构、一份素材/能力矩阵、一套桌面和手机基线图。由我完成检查与草稿；用户提供的比赛时期截图或录屏可用于复核“是否还原”。资料缺失时，明确标记无法判断，不阻止已知问题整改。

通过条件：主回合和保留风格确定；没有新增独立门户或另起一套视觉；不再为了凑完整度继续扩功能。

### 第二工作段：精修一个可投递的主体验

执行：调整首屏与信息层级，处理视频内外的重复信息；围绕已核对事件做三层解释，将原成片与官方教学材料组织到同一体验结构中。

交付：精修的主页面、桌面/手机截图、完整演示路径。先比较效果，再替换线上默认入口；不删除原成片与可回退版本。

通过条件：首屏可见视频；不强制先选模式；关键文字可读；模式差别清楚；来源可追溯；不出现无效功能按钮或错误素材。

### 第三工作段：补足 AI 产品经理作品证据

执行：制作 60–90 秒演示脚本和一页案例说明，整理三项关键产品决策与当前验证；若有可用模型运行条件，补做一条真实问答闭环。模型不可用不阻塞静态演示完善，但不能以静态结果宣称实时能力。

交付：项目链接、演示录屏、案例页、简历四条项目经历，以及能力状态表。

通过条件：用户能讲清本人做了什么、为什么这样取舍、哪些结果有证据；招聘方无需读仓库就能体验主价值。

### 第四工作段：根据优秀作品做有目标的学习

在前述主体验稳定后，再引入参考作品。先选 2–3 个有差异的对象，而不是不断堆积案例。资料分析可与第二工作段并行，但未经判断不直接改线上页面。

交付：每个参考作品一张拆解卡、跨作品比较表及最多五项明确可迁移改进。涉及重构或新增后端时另列成本，不挤占投递版本。

这里的“工作段”是有交付与验收的顺序，不承诺固定工期；先做不依赖新素材、模型和权限的 P0 项。

## 优秀作品的逆向分析方法

输入可以是公开链接、演示视频、截图、作品说明或允许查看的代码。仅凭截图只能判断呈现与交互线索，不能推断其真实模型、后端、用户规模或效果指标。

每份拆解按下列模板输出：

1. **可观察事实**：首屏内容、首次有效操作、主任务路径、反馈状态、展示结果。注明材料与观察位置。
2. **优秀在哪里**：具体到某个交互、解释方式、信息组织或证据呈现，避免“高级感”“很智能”等空泛评价。
3. **可能的机制**：解释为什么有帮助，将推测与已验证实现分开。
4. **与本项目的对应关系**：它解决了我们哪一个已记录的问题？目标用户和使用情境是否相同？
5. **如何迁移**：给出页面位置、行为变化、数据要求与验收任务，不直接复制对方品牌、素材和独有内容。
6. **投入与风险**：现有资产能否支持，需要什么新条件，会不会扩大能力承诺。
7. **决定**：立即采用、做一个小实验、暂不采用，写出理由。

比较维度：首屏价值、任务完整度、AI 解释与控制、结果可信度、视觉层级、异常处理、个人贡献证据。重点是把优秀机制转成自己的可验证设计，不根据漂亮截图虚构技术架构。

## 投递版本的验收清单

- [ ] 招聘方首屏能看到实际体验，不先读长文或被选择弹层挡住。
- [ ] 一个主回合的动作、解释和来源能对应起来，手机上可读。
- [ ] 三种模式的差别有内容意义，不能只换按钮状态。
- [ ] 原版比赛成片保留，官方示例与本人的加工解释有明确区分。
- [ ] 固定解释、模型录制演示、实时问答分别标明，不混用结果。
- [ ] 主演示路径不包含已知失败的视频链接、占位片或开发工具入口。
- [ ] 有一个可直接用于面试的短录屏和一页个人产品案例。
- [ ] 自动化检查、视觉检查和少量外部试用都有记录，不编造效果数据。

## 先做与暂缓

立即推进：首屏、响应式可读性、一个主回合的解释结构、能力证据和短演示。

暂缓：更多球队/比赛扩展、完整实时直播、重新建设大型云端架构、社交分享/商城/赛程扩展、为新颖而增加 Agent 数量，以及没有证据支撑的自动战术结论。

成功标准不是把所有旧功能补齐，而是在保留原作品识别度的前提下，让一个核心体验足够精致、完整、可信，能够支持真实的产品面试讨论。
